# Notes for Claude

UVMC: an Ubuntu VM (Multipass) where an AI agent works only through our supervisor, with a web panel. Read [README.md](README.md), then [docs/guide.md](docs/guide.md) (how everything works) and the "Planned work" section of [docs/design.md](docs/design.md) (what's done, what's next, and why).

## Working here

- **No access outside this project folder (`D:\code\UVMC`) and the folders the user has allowed, unless the user approves it first.** This means reading as well as changing: other files and folders on the PC, app settings, the registry, event logs, services, other processes. It applies to every session and every agent or subagent. Say exactly what you want to look at or do and why, then wait for a clear yes; a yes covers only that one access. Never change anything on the user's system unless they ask for that specific change, and describing a problem is not asking. The `uvmc` VM counts as part of the project.
- Before building on a library or tool (Multipass, llama.cpp, Python packages), check its latest release and bring it up to date first, or say why not.
- Test each step before going on, and explain what you're about to do before building something big. Ask when a request is unclear instead of guessing.
- Try things with test data (`make-testdata` makes `testdata/`), never with the user's real projects.
- The user handles git. Commits use the address 147395095+strat0sf3r@users.noreply.github.com, never a personal email.
- After changing `supervisor/`, the user runs `windows\update.cmd` to push it into the VM. Bump `supervisor/uvmc/__init__.py` so the panel shows which version is running.
- Running commands in the VM from here: with Multipass on Windows (1.16, still in 1.17.0), `multipass exec` keeps one CPU core at 100% the whole time it runs unless its input is a real console window, and Claude Code's shells never give it one. If anything in the VM keeps the command's output open (a `&` job, a server, a test that leaves a process behind), the exec never returns. On 2026-11-09, clients left this way had used hours of CPU. So keep every exec short. Start anything long (the test suite, a preview server) fully detached, then read its log with short execs: `multipass exec uvmc -- bash -c "cd /tmp/x; setsid nohup CMD > run.log 2>&1 < /dev/null &"`. The `&` must apply to that command alone: after a `&&` chain (`cd x && tar ... && setsid nohup CMD ... &`) it puts the whole chain in a subshell that waits for CMD, and the exec never returns (2026-11-10). Never end a command with a bare `&` job that still writes to the exec's output. From a hidden program (no console: the helper, its jobs, `Invoke-VmQuick`), `multipass exec` hangs unless its input is closed (`RedirectStandardInput` then close it; `< /dev/null` on Mac/Linux). `pkill -f PATTERN` inside `bash -c "..."` matches that bash's own command line and kills it first: use `pgrep -f [p]attern` and kill by number. If the PC gets slow, look for leftover `multipass.exe` processes (not `multipassd`) and stop them.

## Private conversations (read before storing anything)

A private conversation must leave nothing behind once it's closed ([private.py](supervisor/uvmc/private.py), guide.md "Private conversations"). **Anything new that stores what a conversation says or does** (a file, a log, a list in memory that outlives it, a message or transcript to another conversation, a line in journald or the audit log) must either skip a private conversation or erase it in `Controller._close` / `_sweep_private`. Then make `tests/test_private.py::test_nothing_left` go through the new place: it runs a private conversation with a marker text and fails if the marker is found anywhere UVMC writes. Name a private conversation to others only through `_about` / `_name_for_others`.

**Never read a private conversation's content** (every session and agent working on UVMC): not its events (`/api/conversations/<id>/events`, `/api/events` while it's current), its log (`/run/uvmc/private`), its copy or its user's files. What you read stays in your own session's transcript, on the PC and with your model's provider, where UVMC can't erase it. Its status is fine (`/api/state` `private`, the conversation list's flags). If a bug can only be found in its content, ask the user to reproduce it in a normal conversation. Being `ubuntu` or root in the VM gives that access until step 7o; this rule is what keeps it unused.

After changes to `setup.sh`, sudo, systemd units, auditd or a new Ubuntu release: the supervisor's start-up check (`private.self_check`) looks for a marker command in journald and the audit log. If the panel says private conversations are off, find what logs the commands again; don't loosen the check.

## Tests

```
cd supervisor
UVMC_NO_SUDO=1 python3 -m pytest -q tests      # or: python3 -m unittest discover tests
```

They run offline with a stand-in model (`FakeClient`, or `Router` in `test_conversations.py`, which answers by the conversation's first task). Also check the panel's script (`node --check` on the `<script>` part of `static/index.html`), `bash -n supervisor/setup.sh`, and `node --check extension/server/index.js`.

To look at the panel without a VM, run it the way the tests do: a `Controller` with a stand-in model, `create_app(ctl, "token")` under uvicorn, then open `/?token=token` in a browser. The README screenshots (`docs/screenshots/`) were made this way, with a fake API key in `ANTHROPIC_API_KEY`.

## Where things are

- `supervisor/uvmc/service.py`: the controller (conversations, approvals, bring-in, resolutions) and every HTTP route.
- `supervisor/uvmc/workcopies.py`: each conversation's copy, the three-way bring-in, resolutions waiting for review, files handed to another conversation.
- `supervisor/setup.sh`: everything installed inside the VM (users, firewall, slices, services). `update` runs it again.
- `extension/`: the Claude Desktop extension; rebuild `uvmc.mcpb` with `npx @anthropic-ai/mcpb pack` after changing it.
- `windows/helper.ps1`, `unix/helper`: the UVMC helper on the PC (guide: "The helper on your PC"): `127.0.0.1:8092` only, its key, the panel's origin and Host checked; runs `local-model` as hidden jobs for the panel (`/pc/...`) and opens the panel signed in (`/panel`). Both answer the panel the same way; change them together. The panel's side is `pcApi` and `pcControls` in `static/index.html`.
- `windows/`, `unix/`: the scripts on the PC. A quick command a script sends to the VM gets `timeout` inside it and is checked with `windows/timeouts.ps1` / `unix/timeouts.sh`, which log timeouts on the PC (guide: "Time limits on the PC's commands to the VM"). Hidden runs (the relay, the extension) also get a limit on the PC (`Invoke-VmQuick`).
